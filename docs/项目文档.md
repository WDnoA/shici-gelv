## 一、项目缘起

### 1.1 问题

AI 大模型的诗词产出速度极快，但**格律质量不稳定**。原因有三：

1. **训练语料里「像诗的文字」远多于「合律的诗」。** 模型学到的是「读起来像」，
   不是「合平仄」。
2. **平水韵与普通话差异巨大。** 入声消失、韵部重组，模型难以从语料中反推正确的中古音。
   例如「东/冬」「支/微/齐」「真/文/元」在普通话里同音或近音，在平水韵里是不同的韵部。
3. **格律是硬约束，不是软偏好。** 模型倾向于把「节奏感」当成「平仄」，
   结果是七字一句读着顺，但二四六位置平仄全错。

### 1.2 人的痛点

人自己校对同样困难：

- 平水韵 106 韵、约 5000 字，背不下来；
- 哪些字是入声，凭语感判断错误率极高；
- 拗救规则（孤平、三平调、特拗）细节繁琐；
- 词牌的句读、韵位更不可能凭记忆核对。

### 1.3 解法

**把「生成」和「校验」彻底分开。**

```
AI 负责才气  +  本项目负责规矩  =  可用的诗
```

本项目只做后者，但把后者做扎实：数据可靠、规则完整、结论清晰、可解释。

### 1.4 为什么不做 AI

| 维度 | 说明 |
| --- | --- |
| **确定性** | 平仄、押韵、对仗都是可判定问题，答案唯一。用规则实现，结论可复现、可追溯。 |
| **可验证** | 若 AI 既生成又评判，它会为自己的偏差背书。规则系统是独立第三方。 |
| **可解释** | 报告能指出「第 4 句第 3 字该仄而用了平，导致三平调」，而不是「重写一遍」。用户能学到东西。 |
| **可持续** | 韵书、词谱是千年沉淀的硬知识，不随模型换代而失效。 |
| **成本** | 零 API 调用、零延迟、可离线。 |

## 三、系统架构

### 3.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│  表现层    web/（原生 HTML/CSS/JS，无构建步骤）               │
│            cli.py（命令行）                                  │
├─────────────────────────────────────────────────────────────┤
│  接口层    api.py      框架无关：handle() 只吃 dict、吐 dict   │
│            server.py   标准库 http.server 胶水（静态文件+路由）│
│            __init__.analyze()  库入口                        │
├─────────────────────────────────────────────────────────────┤
│  编排层    checker.py（近体诗）  ci.py（词）                  │
│            职责：推断体例 → 匹配定式 → 组织各类分析 → 汇总结论  │
│            report.py   把结果对象渲染成文本 / JSON            │
├─────────────────────────────────────────────────────────────┤
│  算法层    patterns.py   诗谱推导、平仄比对、拗救判定、句读诊断 │
│            duizhang.py   节奏切分、词类对照、重字检查          │
│            parser.py     标题/词牌识别、分句、按谱重切         │
│            suggest.py    韵脚换字候选检索                     │
├─────────────────────────────────────────────────────────────┤
│  数据层    knowledge.py  加载知识库、构建反向索引、统一查询     │
├─────────────────────────────────────────────────────────────┤
│  知识库    知识库/**/*.json   （唯一权威数据源，只读）         │
└─────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向**：上层依赖下层，数据层只读知识库，任何代码不写回知识库。

**为什么接口层要独立成 `api.py`**：如果直接把校验逻辑写进 HTTP handler，
将来换框架（FastAPI / Flask / 云函数）就得重写。现在 `api.py` 里没有一行
HTTP 代码——它只处理「请求字典 → 响应对象」，`server.py` 才是那层薄薄的胶水。
换框架的成本因此约等于零。

### 3.2 模块职责

| 模块 | 输入 | 输出 | 关键设计 |
| --- | --- | --- | --- |
| `knowledge.py` | 知识库目录 | `KnowledgeBase` 实例 | 统一把三套韵书转成 `字 → {(韵部, 平仄)}`；词牌建别名索引 |
| `parser.py` | 原始文本 | `ParsedPoem` | 标题判定的歧义消解（见 §4.1） |
| `patterns.py` | 句式表 + 句数 | 诗谱列表 | **不抄诗谱**，由「对」「粘」规则推导 |
| `checker.py` | `ParsedPoem` | `PoemResult` | 四套诗谱各算一遍取最优 |
| `ci.py` | `ParsedPoem` | `CiResult` | 按词谱长度切句，不依赖标点 |
| `duizhang.py` | 两句 | `DuiZhangResult` | 按节奏点切分后逐位对照 |
| `suggest.py` | 韵部名 + 平仄 | 候选字列表 | 只做「韵脚换字」，刻意不做非韵脚建议 |
| `report.py` | 结果对象 | 文本 / JSON | 分栏排版，CJK 宽度对齐 |
| `api.py` | 路径 + 方法 + dict | `Response(status, dict)` | **不含任何 HTTP 代码**，可挂任意框架 |
| `server.py` | — | HTTP 响应 | 仅做静态文件、路由、JSON 编解码；显式覆盖 MIME 类型 |

### 3.3 一次校验的完整流程

```
输入文本
   │
   ├─ parser.parse()
   │     ├─ 去掉 # 注释行
   │     ├─ 判定首行是否标题（歧义消解）
   │     ├─ 从标题提取词牌（若识别到）
   │     ├─ 按标点切句 → clauses
   │     └─ 提取全部汉字 → chars
   │
   ├─ 有词牌？ ──是──→ ci.check()
   │                      ├─ 查词谱 → 按谱长重切 chars
   │                      ├─ 逐句 compare_clause()
   │                      ├─ 按韵标记分组查《词林正韵》
   │                      └─ 输出 CiResult
   │
   └─ 否 → checker.check()
            ├─ infer_shape()  推断五/七言、句数
            ├─ 四种首句式 × build_shi_pu() → 四套诗谱
            ├─ 各算 score_clauses()，取最高分那套
            ├─ 逐句 compare_clause()（含拗救判定）
            ├─ analyze_rhyme()   查《平水韵》
            ├─ analyze_couplets() 颔/颈联对仗
            └─ 输出 PoemResult
   │
   └─ render() / to_json()
```

## 四、关键算法

### 4.1 标题判定（消歧）

**难点**：用户可能这样粘贴——

```
登鹳雀楼
白日依山尽，黄河入海流。
```
也可能这样（每句一行、不打标点）——

```
白日依山尽
黄河入海流
欲穷千里目
更上一层楼
```

两者首行都是「无标点的短行」。更棘手的是「早发白帝城」恰好 5 字，与五言句同形。

**判定策略**（`_looks_like_title`）：

| 条件 | 结论 |
| --- | --- |
| 含 `《》` / `·` / `词牌：` | 标题 |
| 含句末标点且汉字数 ≥ 5 | 正文 |
| 汉字数 > 24 | 正文 |
| 能在其中找到词牌名 | 标题 |
| 汉字数 ∉ {5, 7} 且 ≤ 12 且无标点 | 标题 |
| **汉字数 ∈ {5, 7} 且无标点** | **看剩余内容**：若去掉本行后仍能构成「等长五/七言、偶数句」的体制，则本行是标题；否则是正文 |

最后一条是关键。测试用例：

| 输入首行 | 剩余内容 | 判定 |
| --- | --- | --- |
| 登鹳雀楼（4 字） | — | 标题（规则 5） |
| 早发白帝城（5 字） | 4 个七言句 → 合法 | **标题** |
| 白日依山尽（5 字） | 3 个五言句 → 句数非法 | **正文** |

### 4.2 诗谱推导（不抄诗谱）

近体诗的一切句式，都由**四种基本句式**按**对、粘**规则排列而成。
知识库只存 4 条句式 + 2 条规则，程序推导出全部 16 种诗谱。

**四种基本句式**（以《第二字》《收尾》为键）：

| 字数 | 第二字 | 收尾 | 句式 |
| --- | --- | --- | --- |
| 五言 | 仄 | 仄 | 仄仄平平仄 |
| 五言 | 平 | 平 | 平平仄仄平 |
| 五言 | 平 | 仄 | 平平平仄仄 |
| 五言 | 仄 | 平 | 仄仄仄平平 |
| 七言 | 平 | 仄 | 平平仄仄平平仄 |
| 七言 | 仄 | 平 | 仄仄平平仄仄平 |
| 七言 | 仄 | 仄 | 仄仄平平平仄仄 |
| 七言 | 平 | 平 | 平平仄仄仄平平 |

**两条规则**：

```python
对句(prev) = 句式表[(翻转(prev.第二字), 平收)]     # 同一联内，第二字相反，且押韵
粘句(prev) = 句式表[(    prev.第二字 , 仄收)]     # 上下联之间，第二字相同，且不押韵
```

**推导**：首句式确定后，第 2 句取对句；第 3 句起，偶数句取对句、奇数句取粘句。

**验证**（程序内置断言，测试覆盖）：以「仄仄平平仄」开头，推导结果必然是

```
仄仄平平仄 / 平平仄仄平 / 平平平仄仄 / 仄仄仄平平
仄仄平平仄 / 平平仄仄平 / 平平平仄仄 / 仄仄仄平平
```

与传世五律「仄起仄收式」完全一致；七言同理得到「仄仄平平仄仄平」开头的标准七律谱。

> **收益**：知识库里不会出现「同一首诗谱抄了 16 遍、改一处忘另一处」的问题。

### 4.3 平仄比对与状态机

每个字判定后落入五种状态之一：

| 状态 | 含义 | 计分 |
| --- | --- | --- |
| `合律` | 与定式一致 | ✔ |
| `从宽` | 位置属「一三五不论」，虽不合定式但允许 | ✔ |
| `借读` | 该字为多音字，另一种读法可满足定式 | ✔ |
| `未收录` | 韵书中查无此字 | **不计入分母** |
| `出律` | 以上皆非 | ✘ |

**处理顺序**（先命中者为准，见 `知识库/格律/拗救与特殊句式.md` §8）：

```
1. 与定式完全一致                    → 合律
2. 差异落在「不论」位置                → 从宽
3. 多音字的另一读法可满足              → 借读
4. 整句符合「特拗」变体                → 合律（把该句出律标记改回合律）
5. 整句符合「半拗」                    → 合律
6. 该句犯孤平但符合拗救式              → 合律
7. 该句犯孤平 / 三平调                 → 出律（大忌）
8. 该句犯三仄尾                        → 警告（小病）
9. 其余不符                            → 出律
```

**关键细节：孤平的判据。**

孤平**只可能**出现在「…仄仄平」结尾的押韵句，即「平平仄仄平」与「仄仄平平仄仄平」
这两个句式被拗改之后。若不加此限制，「仄仄仄平平」这类**定式本身**只有
「仄」一平（除韵脚外），会被误判为孤平。

```python
if pattern[-1] == 平 and actual[-2] == 仄:      # ← 这一条是关键
    if actual[:-1].count(平) <= 1:
        saved = actual[n - 3] == 平              # 第三字(五言)/第五字(七言)用平声救回
```

**特拗句的识别**：五言「平平仄平仄」、七言「仄仄平平仄平仄」，
因其首字位属「不论」，故只核对后四字的关键特征「平仄平仄」：

```python
五言: 定式 == "平平平仄仄"    and actual[1:] == "平仄平仄"
七言: 定式 == "仄仄平平平仄仄" and actual[3:] == "平仄平仄"
```

### 4.4 定式匹配（择优）

一首诗有四套候选诗谱（四种首句式）。做法是**各算一遍取最高分**，而非先猜首句。

```
score(谱) = 合律字数 / (总字数 − 未收录字数)
```

平手时优先选「首句不入韵」的格式（近体诗主流）。

**为什么不用「从首句反推」？**
因为首句本身可能出律，反推会把误差传播到全篇。全局择优更稳健。

### 4.5 押韵分析

**步骤**：

1. **定韵脚**：所有**平收句**（定式末字为平）即押韵句；
2. **定主韵**：统计非首句韵脚所属韵部的出现次数，取众数；
3. **逐个核对**：
   - 韵部含主韵 → ✔
   - 是首句且与主韵互为**邻韵** → ✔（首句借韵，传统允许）
   - 其余 → ✘ 出韵
4. **重韵检查**：韵脚字重复 → 提示
5. **仄韵变体探测**：若全部韵脚皆为仄声 → 提示「疑似仄韵诗变体」

### 4.6 词韵：半韵问题

《词林正韵》把平水韵 106 韵归并成 19 部，但有**八处「半韵」**——
同一个平水韵部按古音的开合洪细被拆入两个词林部：

| 平水韵部 | 拆分依据 | 例字 |
| --- | --- | --- |
| 上平十灰 | 合口 → 第三部 / 开口 → 第五部 | 杯回↔台来 |
| 上平九佳 | 开口 → 第五部 / 齐齿 → 第十部 | 街鞋↔佳涯 |
| 上平十三元 | 合口 → 第六部 / 开口 → 第七部 | 魂门↔元原 |
| 上声十三阮 | 同上 | 本损↔阮远 |
| 上声十贿 | ui/ei → 第三部 / ai → 第五部 | 贿悔↔改采 |
| 去声九泰 | 合口 → 第三部 / 开口 → 第五部 | 会外↔泰带 |
| 去声十卦 | ai → 第五部 / ua → 第十部 | 怪拜↔画话 |
| 去声十四愿 | 同上 | 论寸↔愿怨 |

实现方式：`知识库/韵书/词林正韵.json` 的 `部映射` 给**默认归属**，
`半韵字表` 做**字符级覆盖**。

**难点**：宋词实际用韵中，半韵常通押。例如晏殊《浣溪沙》：

```
一曲新词酒一杯，去年天气旧亭台。夕阳西下几时回。
无可奈何花落去，似曾相识燕归来。小园香径独徘徊。
```

「杯、回、徊」属第三部，「台、来」属第五部——按严格切分竟是出韵，
但这是传世名篇。故引入 `半韵通押组`：

```json
"半韵通押组": { "组": [["第三部","第五部"], ["第五部","第十部"], ["第六部","第七部"]] }
```

命中时**只作提示，不判出律**，并在报告中注明「属半韵通押，宋词多可通融」。

> 设计取舍：**宁可标注不确定，不可制造假阳性。** 工具一旦误报，用户就会失去信任。

### 4.7 词：按谱切句

词的标点千变万化，用户抄录时又常漏标点。因此**不依赖标点**，而是：

```
提取全部汉字 → 按词谱的每句字数依次切分
```

例如「水调歌头」正体的句长序列为
`[5,5,6,5,6,6,5,5,5, 3,3,3,4,7,6,6,5,5,5]`，合计 95 字。
切分后与词谱逐句比对。

**顺带好处**：若用户标点与词谱句读不符，也会被间接发现（字数对不上）。

**词谱的韵标记语义**：

| 标记 | 含义 | 处理 |
| --- | --- | --- |
| 0 | 不押韵 | 跳过 |
| 1 | 押韵 | 延续当前韵组 |
| 2 | 叠韵 | 检查末字是否与上一韵脚相同 |
| 3 | 换韵 | 开新韵组 |
| 4 | 叶韵 | 与前韵同部而平仄不同 |

韵组内独立检查：韵部一致性 + 韵脚平仄是否与词谱收尾相符。

### 4.8 对仗分析

**能自动做的**：

1. **节奏切分**：五言 `2-2-1`，七言 `2-2-2-1`，九言 `2-2-2-2-1`；
2. **词类对照**：查 `知识库/对仗/词类分类.json`（20 门类），
   逐位统计门类重合情况：
   - 全部位置门类相同 → **工对**
   - 门类部分相同、词性相当 → **宽对**
   - 平仄不相对 → **平仄失对**
3. **重字检查**：出句与对句共用字 → 提示

**不能自动做的**：合掌、流水对、借对、当句对、意境高下。报告中明确声明。

### 4.9 句读错位诊断

**问题**：词的「句读」是词谱的一部分。作者常按语义自然地打逗号，
但词谱可能要求不同的顿断位置。典型例子（苏轼《水调歌头》）：

```
词谱：中平中仄平仄，中仄仄平平   →  6 字 + 5 字
苏轼：不知天上宫阙，今夕是何年

作者：桂影婆娑处，清辉漫洒芳丛   →  5 字 + 6 字（总字数相同，只是「逗」错位）
```

**天真的做法**是按谱长硬切，会切出「桂影婆娑处清」这种跨句拼接的怪句——
输出毫无意义，只会让人困惑。这是本项目开发过程中真实踩过的坑。

**正确做法**分三步：

1. **切句时优先尊重作者标点**：只要「句数一致 + 总字数一致」，就按作者的标点分句，
   不使用谱长硬切。这样报告能精确指出「第 3 句应 6 字、实 5 字」。
2. **把连续的字数不符句归为一段**，检查该段总字数是否等于词谱对应各句的总字数。
3. **按谱长重新断句，再验平仄**：

| 重断结果 | 结论 | 报告措辞 |
| --- | --- | --- |
| 平仄全合 | 用字没问题，只是「逗」放错 | `[建议] 问题在「逗」的位置` |
| 仍有出律 | 不只是逗位问题，需调整用字 | `[错误] 句读错位且平仄不合`（列出不合处） |

**为什么措辞要谨慎**：挪逗号不改变字序，所以「平仄全合」只说明这串字**能**按谱断，
不代表断出来一定通顺。报告因此写「照上面重断即可（**语义请自行核对**）」，
而不是「一字不必改」。

### 4.10 韵脚换字建议

**只做韵脚，不做其他位置。** 这是有意为之的边界：

| | 韵脚 | 非韵脚出律字 |
| --- | --- | --- |
| 目标空间 | **封闭**：只需在主韵部里找一个平仄相符、未用过的字 | **开放**：任何仄声字理论上都可以 |
| 能否确定 | 能——韵部与平仄都是硬约束 | 不能——还取决于句意、搭配、语感 |
| 结论 | 给出候选清单 | 只说明「此处需仄声」 |

**排序策略**（没有词频表，用两个代理信号代替）：

1. **诗词常用字优先** —— 以 `知识库/对仗/词类分类.json` 所收的 930 字
   作为「常见诗词用字」的近似。这样同音的生僻字（如「童」旁的僮、瞳、潼）
   就不会挤在候选清单前面。
2. 其余按**韵书原本的排列次序**。

> 开发中曾因 `词林正韵` 加载时误用 `set` 丢了字序，导致候选字乱成一团
> （「充、沣、冯、聪、螽、珑、衷、瞳……」）。改用保序的 list 后恢复正常。

**输出示例**：

```
● [建议] 押韵换字建议：「波」不在主韵《词林正韵》第一部（该韵位需 平声）。
  可从主韵部中选平声字替换，例如：东、铜、桐、中、虫、终、弓、宫、熊、穷、
  风、枫、功、红、虹、翁、蓬、冬、钟、龙、松、胸、重、从……
  （仅按韵部与平仄筛出，语义是否相合请自行斟酌）
```

### 4.11 句读骨架

在词的报告顶部列出一行「各句字数」，供作者在动笔时对照：

```
句读骨架：5·5·6·5·6·6·5·5·5·3·3·3·4·7·6·6·5·5·5
```

比「字数 95」有用得多——填词失败往往不是总字数错，而是**每一句的字数分布错**。

## 五、知识库设计

### 5.1 为什么把数据放在 JSON 而不是代码里

| | 放代码里 | 放 JSON（本项目） |
| --- | --- | --- |
| 改一个字的平仄 | 改代码、重编译、回归测试 | 改 JSON、重启即可 |
| 非程序员能否维护 | ❌ | ✅ |
| 数据能否复用 | ❌ | ✅（APP、其他语言都能读） |
| 数据错误能否发现 | 淹没在代码里 | `--verify-kb` 一键自检 |
| 会不会被逻辑污染 | 会 | 不会 |

### 5.2 三套韵书的数据结构

**平水韵**（字表式）

```json
{
  "韵部": {
    "上平声": { "一东": "东同铜桐筒童…" },
    "上声":   { "一董": "董懂动孔总笼…" },
    "入声":   { "一屋": "屋木竹目服福…" }
  },
  "邻韵": { "组": [["上平声一东","上平声二冬"], …] }
}
```

- 平仄由所在大类推导：`上平声/下平声 → 平`，`上声/去声/入声 → 仄`
- 字串以空格分隔（本项目为使排版紧凑、便于比对，实际写作连续字串）
- 反查索引 `字 → [(韵部, 平仄)]` 在加载时构建

**词林正韵**（映射式，不重复抄字表）

```json
{
  "部映射":   { "第一部": { "平": ["上平声一东","上平声二冬"], "上": [...], "去": [...] } },
  "半韵字表": { "上平声十灰": { "第三部": "灰恢魁隈回…", "第五部": "开哀埃台苔…" } },
  "半韵通押组": { "组": [...] }
}
```

> **关键**：词林正韵的每个字都从平水韵推导而来，
> 因此**补录平水韵会自动同步到词林正韵**，永不脱节。

**中华新韵**（规则式 + 运行时计算）

```json
{ "韵母归属": { "一麻": ["a","ia","ua"], "十唐": ["ang","iang","uang"], … } }
```

字 → 韵部的转换在运行时由 `pypinyin` 完成。因为依赖拼音，故设计为**可选**：
未安装时程序正常运行，只在显式选用新韵时给出安装提示。

### 5.3 词谱数据结构

```json
{
  "浣溪沙": {
    "别名": ["浣纱溪", "小庭花", "满院春", "东风寒"],
    "字数": 42, "段数": 2, "句数": 6, "韵": "平韵(5韵)",
    "对仗": ["下片第4、5句多用对仗"],
    "格律": [
      { "谱": "中仄中平中仄平", "韵": 1 },
      …
    ]
  }
}
```

- `谱` 中 `平/仄/中` 分别表示「应平」「应仄」「不拘」
- `韵` 用 0/1/2/3/4 编码（见 §4.7）
- `顿号` 在谱中保留（如 `"中中仄、中平中仄平仄"`），仅作显示，比对时剥离

### 5.4 数据完备度与自检

| 数据 | 规模 |
| --- | --- |
| 平水韵 | 约 3500 字 / 106 韵 |
| 词林正韵 | 19 部（含 8 处半韵的字级拆分） |
| 中华新韵 | 14 韵 |
| 词牌 | 31 个（含别名 138 条） |
| 对仗词类 | 20 门 / 约 930 字 |

`--verify-kb` 自检项：

1. 每个韵书非空；
2. 统计一字多归属的数量（多音字，属正常）；
3. 近体诗诗谱能正常推导（五言/七言 × 4 式，各推 8 句）；
4. **每个词牌的谱长 == 标称字数**，句数 == 格律条目数；
5. `pypinyin` 是否可用。

> 第 4 项在开发中**实际抓出了 3 个词牌的谱长错误**（水调歌头 96≠95、
> 念奴娇 88≠100、沁园春 110≠114）。这正是自检的价值。

## 六、接口设计

### 6.1 库接口

```python
from poetry_checker import analyze

r = analyze(text, kb=None, book="平水韵", shape="auto")

r.kind      # "近体诗" | "词" | "未知"
r.ok        # bool   是否合律
r.score     # float  平仄符合度（只就已判定字而言）
r.coverage  # (int, int) (已判定字数, 总字数)
r.parsed    # ParsedPoem
r.poem      # PoemResult  | None
r.ci        # CiResult    | None
r.text()    # str  中文报告
r.to_dict() # dict 结构化结果（供 API / 前端）
r.json()    # str  同上，JSON 字符串
```

> `analyze` 会自动复用传入的 `KnowledgeBase`；
> 批量处理大量诗词时应**显式传入同一个 kb 实例**，避免重复加载。
> API 服务就是这么做的——进程内常驻一份，并按文件指纹自动热重载（见下）。

#### `score` 与 `coverage` 必须一起用

`score` 只统计韵书里查得到的字。查不到的字（生僻字、韵书漏收、整句字数与定式不符）
**既不算对也不算错，直接不进分母**——分母变小，分数反而更高。
于是一首诗哪怕有一半的字没查过，`score` 也能是 `1.0`。

这不是假设。真实投稿《中秋寄知音》的句 6「幽怀千缕各沉吟」中，
「各」「沉」「缕」三字当时都未收录，报告却印出「合律 100%」。

因此：

- `score` 是「在已判定字中，合律的占比」，**不是**「这首诗有百分之多少合律」；
- `coverage` 给出 `(已判定字数, 总字数)`，`known < total` 时结论只对已判定字成立；
- 报告会写成「平仄符合度 100.0%（已判定 53/56 字）」，并多给一行 ⚠ 提示；
- HTTP 接口的 `coverage` 字段、前端「已判定字数」一行，都是同一个信息。

**只看 `score` 会被误导。任何展示 `score` 的地方都必须同时展示 `coverage`。**

#### 知识库热重载

`CheckerAPI` 在进程内常驻一份知识库，但**不是**一劳永逸：每个接口被调用前都会
比对一次数据文件的指纹（路径 + 字节数 + 修改时间），变了就整体重载。

理由是踩过坑：本项目最核心的用法就是「碰到未收录字 → 查证 → 补录进 JSON」。
若改完必须重启服务才生效，使用者会以为**补录失败了**。真实发生过——
把「冷」补进平水韵后，页面照旧报「冷」未收录，因为进程里还是几小时前那份数据。

两个细节：

- **重载失败时保留旧数据**，绝不因为 JSON 正编辑到一半（语法错误）而把服务打挂。
  下次请求会再试，直到文件合法为止。
- **`auto_reload=False` 可关闭**，测试与对一致性有严格要求的场景用得上。
- `/api/meta` 会回报 `kb_reload_count`，排查「补录了却不生效」时先看它。

### 6.2 HTTP 接口

接口层 `api.py` **不含任何 HTTP 代码**，只做「请求字典 → Response 对象」：

```python
class CheckerAPI:
    def handle(path: str, method: str = "GET", body: dict | None = None) -> Response
```

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/meta` | 版本、韵书清单（含字数、新韵可用性）、词牌数、字数上限 |
| `GET` | `/api/cipai` | 词牌一览：正名、别名、字数、段数、句数、韵式 |
| `POST` | `/api/check` | 校验，body：`{"text": "...", "book": "平水韵", "shape": "auto"}` |

**成功响应**

```json
{ "ok": true, "result": { "kind": "近体诗", "ok": true, "score": 1.0, ... } }
```

**失败响应**（一律带 HTTP 状态码）

```json
{ "ok": false, "error": "文本过长（5000 字），单次最多 4000 字" }
```

| 状态码 | 触发条件 |
| --- | --- |
| `400` | `text` 缺失/为空、超过 4000 字、`book` 或 `shape` 取值非法、body 不是合法 JSON |
| `404` | 未知接口路径、静态文件不存在 |
| `405` | 方法与接口不匹配 |
| `413` | 请求体超过 1 MB |
| `500` | 知识库损坏等内部错误 |

### 6.3 结果结构

`result` 即 `AnalysisResult.to_dict()`，刻意**不含 `kb`**（知识库实例不可序列化，前端也用不上）：

```json
{
  "kind": "近体诗",
  "ok": true,
  "score": 1.0,
  "message": "",
  "parsed": { "title": "春望", "clauses": ["国破山河在", ...], "chars": "..." },
  "poem": {
    "genre": "五言律诗",
    "pattern_label": "仄起仄收·首句不入韵",
    "pattern": ["仄仄平平仄", "平平仄仄平"],
    "clauses": [
      {
        "index": 0, "text": "国破山河在", "pattern": "仄仄平平仄", "is_rhyme": false,
        "chars": [
          { "index": 0, "char": "国", "expected": "仄",
            "tones": ["仄"], "status": "合律", "chosen": "仄" }
        ],
        "issues": []
      }
    ],
    "rhyme":   { "book": "平水韵", "main_group": "下平声十二侵", "feet": [], "consistent": true },
    "couplets": [],
    "issues": [], "score": 1.0, "verdict": "合律"
  },
  "ci": null
}
```

> **注意**：`shared`（词类交集）、`skeleton`（句读骨架）、`ok`（子对象上的）等是
> Python 的 `@property`，不会被序列化。前端按需自行计算，例如句读骨架就是
> `clauses.map(c => c.pattern.length).join('·')`。

### 6.4 前端

`web/` 是原生 HTML/CSS/JS，**无打包、无依赖**。页面只做三件事：

1. `GET /api/meta` 初始化韵书下拉框；
2. `POST /api/check` 拿结果；
3. 把逐字平仄画出来——**平=青蓝、仄=赭黄、出律=红底加粗下划线**，
   鼠标悬停任意字弹出该字的定式要求与韵书归属。

设计上刻意把「判定」全部留给后端：前端没有一行格律逻辑，
因此换皮、改版、移植到别的框架都不会碰到正确性。

### 6.5 命令行

```
python main.py [文件] [-t 文本] [-b 韵书] [--shape 诗|词] [--json]
               [--brief] [--no-color] [--verify-kb] [--list-cipai]
               [--serve] [--port 8765] [--no-browser]
```

退出码：

| 码 | 含义 |
| --- | --- |
| `0` | 命令正常完成 —— 合律／合谱／仄韵变体／**无法识别体裁** |
| `1` | 存在出律 |
| `2` | 知识库加载失败，或 `--expect` 的目录不存在／无 `.txt` 文件 |

> 「无法识别体裁」返回 `0` 而不是 `1`：程序本身跑完了，只是判不出体制，
> 不当成失败。**文本模式与 `--json` 必须给出相同的退出码**——
> 这里曾经不一致（文本模式返回 1、`--json` 返回 0），
> 是 `Test命令行.test_无法识别仍返回0` 抓出来的。

### 6.6 Windows 启动器

给不习惯命令行的使用者准备的两个批处理：

| 文件 | 作用 |
| --- | --- |
| `启动校验器.bat` | 双击启动服务并自动开浏览器 |
| `停止校验器.bat` | 双击停止服务 |

**启动器要处理的几件事**（都不是想当然的）：

1. **找 Python** —— 系统里可能是 `python`，也可能只有 `py` 启动器，都要试。
2. **切控制台编码** —— 批处理文件本身是 UTF-8，不先 `chcp 65001`，
   `echo` 出来的中文在中文 Windows 上会乱码。
3. **统一子进程编码** —— cmd 的 echo 走 UTF-8，而 Python 默认按本地编码（cp936）写，
   一个窗口里两种编码必然花屏。必须同时设 `PYTHONIOENCODING=utf-8`。
4. **端口占用要容错** —— 双击场景下「自动换端口」远好过「报错退出」。
5. **找不到文件时给出人话提示**，而不是让窗口一闪而过。

**停止脚本的安全设计**：只杀「监听候选端口 **且** 进程名以 `python` 开头」的进程。

> 这条不是空想。开发机上 8080 端口被系统的 `AgentService.exe` 占着——
> 如果停止脚本只按端口杀，就会误杀一个系统服务。

**开机自启**：`Win+R` → `shell:startup` → 把启动器快捷方式拖进去。

### 7.1 测试固件与 `示例/` 解耦

**这是交付过程中暴露出来的一个真问题。**

原本 `Test句读诊断` 直接读 `示例/10-用户投稿-水调歌头-中秋寄魏晓彤.txt`。
而 `示例/` 是**给使用者看的展示目录**——使用者照着校验报告把这首词改好了
（改成「桂华浮动清影，清露滴芳丛」），结果依赖旧文本的测试当场失败。

根因不是使用者改了文件，而是**测试依赖了不该依赖的东西**：

| | `示例/` | `tests/fixtures.py` |
| --- | --- | --- |
| 定位 | 给人看的展示 | 给测试用的冻结数据 |
| 谁可以改 | 使用者随便改 | 只有维护者 |
| 测试能否依赖 | **不能** | 应该 |

因此把所有断言用到的文本内联到 `tests/fixtures.py`，
`读()` 改为查固件字典，**不再碰文件系统**。
`示例/` 只剩一条内容无关的健壮性测试（只断言「不抛异常、能出报告」）。

顺带加了两条：

- `test_按报告改定后应合谱` —— 锁住「建议的有效性」：
  使用者照报告改完确实 100% 合谱。若哪天改坏了句读判定或韵书数据，这条会红。
- `test_修订稿与实际示例文件一致` —— 发现「示例与固件脱节」时跳过并提示同步，
  而不是把使用者的正常编辑当成失败。

> `TestHTTPServer` 用的是**真的 `http.server`**（起线程、绑定随机空闲端口、
> 用 `urllib` 发请求），而不是 mock。因为它要验证的东西——MIME 类型、
> 目录穿越防护、HTTP/1.1 的 Content-Length ——恰恰是 mock 测不到的。
>
> 这个测试在开发中**真的抓到了 bug**：Windows 注册表把 `.js` 映射成 `text/plain`，
> 浏览器会拒绝执行脚本。现在 `server.py` 显式覆盖常见前端资源的 MIME 类型。

> 其中 `test_只是逗位问题则不必改字` 用的是一份**人为挪动逗号**的苏轼《水调歌头》：
> 把「不知天上宫阙，今夕是何年」写成「不知天上宫，阙今夕是何年」。
> 字数不变、平仄不变，程序应当且只能报出「逗的位置不对」。这是句读诊断的核心用例。

## 九、开发规范

### 9.1 加一个新的字

1. 查证该字在平水韵中的归属；
2. 打开 `知识库/韵书/平水韵.json`，在**对应韵部字符串末尾**追加；
3. 运行 `python main.py --verify-kb`；
4. 词林正韵会自动同步（从平水韵推导）。

### 9.2 加一个新的词牌

1. 在 `知识库/词谱/词牌格律.json` 的 `词牌` 对象下新增一条；
2. 逐句列出 `谱` 与 `韵` 标记；
3. 运行 `--verify-kb` 核对「谱长 == 字数」「句数 == 格律条目数」。

### 9.3 通用原则

- **不要硬编码任何字**到 Python 里。想问「这个字是平是仄」，只能调 `kb.tones()`。
- **不要重复存数据**。能推导的就推导（如词林正韵、诗谱）。
- **宁可留白**。无法判断时输出「未收录」「仅供参考」，绝不猜测。
- **改完跑测试**。`python -m unittest discover -s tests`。

### 10.1 术语表

| 三平调 | 押韵句末三字全平，大忌 |

| 半拗 | 「仄仄仄平仄」，只拗不忌，可不救 |
| 拗救 | 在本句或对句的相应位置作平仄补偿 |
| 借韵 | 首句借用邻韵，传统允许 |
| 词牌 | 词的格式名，规定句数、字数、平仄、韵位 |
| 换韵 | 一首词中途更换韵部 |
| 叶韵 | 同一词林部内平仄通押 |

### 11.4 一次真实故障：所有页面 404

交付前测试时踩到的，值得记下。

**现象**：浏览器打开只有一行 `{"ok": false, "error": "文件不存在"}`，
连首页都打不开；但 `/api/meta` 却正常返回 200。

**原因**：端口上跑着的是一个**指向已删除目录的残留进程**——
测试时把项目复制到临时目录、起了服务，清理时删了目录，却没杀掉 python 子进程
（`proc.kill()` 只杀了 `cmd`，没杀它的子进程）。那个进程的 `WEB_DIR`
已经不存在，于是**所有**静态请求都 404；而知识库在启动时已读进内存，
所以 API 依然活着。

**诊断线索**：`API 正常但页面全 404` 这个组合，几乎只可能是「静态目录没了」。

**三处修复**：

| 修复 | 说明 |
| --- | --- |
| 404 页面改头换面 | 不再是 JSON，而是 HTML：列出服务在用的目录、该目录是否存在、里面有哪些文件，并给出排查步骤 |
| `/api/meta` 增加字段 | `web_dir` / `web_ok`，一眼看出服务指向哪儿 |
| 停止脚本加第二道网 | 除了按端口扫，还扫「命令行含 `server.py` 且不是 `-c` 内联脚本」的 python 进程，捕获不在候选端口上的孤儿 |

另外把浏览器的 `/favicon.ico` 从 404 改成 **204**（页面已声明 SVG 图标），
免得控制台里有一条常驻红色报错。

**给使用者的提示**：服务运行期间不要移动或重命名项目文件夹——
启动横幅里写了这句话。
